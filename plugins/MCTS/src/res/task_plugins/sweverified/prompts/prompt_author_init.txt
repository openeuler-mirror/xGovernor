# Phase 2: Derive the contract from the task

Start from `PROBLEM_STATEMENT` and, when present, `REQUIREMENTS`/`INTERFACE`. Read them line by line before opening product code.

Create a requirement checklist covering every distinct:

- stated scenario, workflow, example, expected/actual behavior, error message, output, or SQL fragment;
- implied layer or entry path;
- mentioned or necessary boundary and failure mode;
- non-goal that prevents scope drift.

For every proposed expectation, classify its evidence:

1. explicit task/interface contract;
2. established project contract consistently demonstrated by upstream tests or public behavior;
3. inference about intent.

Test (1) exactly and (2) without expanding it. Never turn (3) into a mandatory wording, representation, workflow, side effect, or invariant. If the exact post-fix result is unspecified, assert only the smallest semantic or structural correction supported by the task and established behavior. A minimal correct fix that changes only the requested behavior must pass.

Apply a strict scope lock: every test must map to a checklist requirement or a necessary discriminator against a plausible partial fix. Do not invent requirements such as rollback, atomicity, copying, persistence, stacking, serialization, unrelated operations, or extra supported inputs.

Only after the checklist is complete, read the minimum product code needed to map each item to an observable public behavior. For each item ask:

- Which code path does it exercise?
- Where is the symptom observed, and which shared public API or established reusable behavior owns the same semantics one level below it?
- Which other legitimate callers or entry paths use that shared behavior?
- Could a one-file or one-layer patch pass while leaving this item broken?
- What plausible shallow fix should this test reject?

Build a compact behavior-propagation map for each requirement: visible symptom → immediate caller → shared public API/established reusable behavior → other legitimate entry paths. When the same task-required semantics are an explicit or established contract at more than one of these points, test both the visible scenario and the distinct shared/alternate entry path. Do not test private implementation location merely to force the golden patch; constrain observable contracts, while rejecting a caller-only compensation that leaves the same established behavior broken elsewhere.

Stop reading when every item has an assertion strategy or two additional focused reads add nothing.

# Phase 3: Generate the suite

Write `/home/user/workspace/repo/testcases.py`. Each test must name its scenario and satisfy all applicable rules:

- Problem-anchored: traceable to the checklist, not invented from code alone.
- Two-sided: a Fail-to-pass case fails on buggy product behavior and passes after a complete correct fix; a narrow regression case may pass on both.
- High-discrimination: rejects realistic shallow or partial fixes rather than acting as a smoke test.
- Broad and diverse: cover every explicit aspect and distinct relevant path, favoring different behaviors over literal variations.
- Precise but evidence-bounded: exact messages, formatting, SQL, structures, sequences, and side effects only when supported by an explicit or established contract.
- Observable: call product APIs and assert results, exceptions, messages, SQL, properties, or side effects. Never manufacture failure with intentionally unequal literals.

For exact-output defects, assert the complete relevant expected value or justified structure. Keyword-only checks and merely forbidding the old value are too weak, but do not guess unspecified exact wording.

Cover every checklist item and every relevant layer described by the task. Write at least 6 high-discrimination cases with no upper limit: all relevant Fail-to-pass cases and necessary discriminators, plus only a small number of narrow regressions. Never pad with unrelated cases.

Before validation, perform a counterfactual partial-fix attack. Imagine at least: (1) a patch that compensates only in the most visible caller, and (2) a patch that handles only the report's easiest example, relationship, input, or path. If either patch could pass the whole suite while the same justified behavior remains broken through another legitimate public/established entry path, add a discriminator for that missing path. Prefer a new layer or entry path over more parameter variations in an already covered path.

Then ask for every case: “Would a minimal complete correct fix pass?” Ask for the suite: “Would a plausible caller-only or one-layer fix still fail somewhere for a justified behavioral reason?”
